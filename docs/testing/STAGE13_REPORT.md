## 3. Проверка безопасности: найдено и исправлено

| Находка | Риск | Исправление |
|---|---|---|
| Нет общего ограничения частоты запросов | перебор, перегрузка | лимит по IP в Redis (общий для всех экземпляров), строже для входа; 429 с `Retry-After`; тест |
| Нет защитных HTTP-заголовков | кликджекинг, MIME-sniffing | helmet (HSTS, nosniff, frame-options), убран `X-Powered-By`; тест |
| Документация API открыта в production | раскрытие структуры | Swagger выключен в production по умолчанию |
| WebSocket: подписка сразу после подключения могла потеряться | пропуск событий | проверка токена перенесена в middleware Socket.IO (до установки соединения); неавторизованное соединение отклоняется сразу |
| Уязвимости в зависимостях (`pnpm audit`) | 2 средних в react-router админки | обновлён до 7.18; остаётся 1 средняя в инструменте сборки Expo (`minimatch`, не попадает в приложения) |
| Проверено и в порядке | — | токены и cookie маскируются в логах; SQL только параметризованный (единственный `sql.raw` — с константой); тестовые провайдеры запрещены в production; Docker-образ работает от непривилегированного пользователя |

## 4. Нагрузочное тестирование подбора

Сценарий (`apps/api/test/load/matching.load-spec.ts`, результат — `load-matching.json`): 100 компаний, 300 единиц
техники, 300 машинистов, 20 заказчиков; 200 заказов создаются по 20 параллельно; подбор — 4 параллельных обработчика
(как 4 экземпляра сервера); затем на каждое предложение — 5 одновременных «Принять».

| Показатель | Значение |
|---|---|
| Расчёт цены, p50 / p95 | 167 / 313 мс |
| Создание заказа, p50 / p95 | 93 / 147 мс |
| Подбор 200 заказов (4 обработчика) | 8,5 с (~23 заказа/с) |
| Заказы с предложением | 200 из 200 |
| Принятие, p50 / p95 | 210 / 270 мс |
| Гонка принятий | 1000 попыток → 200 принято, 800 отклонено как повтор, 0 ошибок |
| Инварианты | ни одного заказа с двумя активными предложениями или двумя принятиями; брони техники не пересекаются |

**Найдено нагрузкой и исправлено:**

1. **Зависание сервера при 20+ одновременных заказах.** Настройки платформы читались отдельным соединением внутри
   транзакций; когда все соединения пула заняты транзакциями, они ждали друг друга бесконечно. Исправлено: снимок
   настроек в памяти (обновление в фоне каждые 5 с и сразу после изменения).
2. **Одна техника получала предложения по двум заказам на одно время** — второе принятие упиралось в «техника
   занята» (9 из 200 заказов возвращались в поиск). Исправлено (С-37, ждёт «ок»): пока предложение открыто, та же
   техника на пересекающееся время второе не получает. Повторный прогон: 200 из 200.

**Ограничения измерения:** маршрутизация тестовая — с Яндекс Маршрутизацией к расчёту цены и подбору добавится
время её ответа (несколько вызовов на заказ); прогон перемерить после получения ключа. «Время до первого
предложения» в отчёте завышено устройством теста (сначала создаются все 200 заказов, потом запускается подбор).

## 5. Резервное копирование и восстановление

`infra/backup/backup.sh` → копия базы (pg_dump) + файлов + контрольные суммы + контрольные показатели.
`infra/backup/restore.sh` → восстановление в **новую пустую** базу одной транзакцией и сверка.

Результат на демо-базе: контрольные суммы совпали; 64 таблицы — число строк совпало; сумма проводок = 0;
суммы оплат и возвратов совпали; 12 миграций с контрольными суммами, триггеры защиты, ограничение EXCLUDE,
расширения PostGIS и btree_gist на месте; 4 файла восстановлены. Сервер, запущенный на восстановленной базе,
отвечает (health), вход и список заказов работают.

## 6. Готовность к реальным провайдерам

Проверены все интерфейсы (`docs/INTEGRATIONS.md`). Чтобы подключение не потребовало переделок, на этапе 13 сделано:
асинхронные возвраты и выплаты с итогом по уведомлению; возврат вызывается после фиксации транзакции; асинхронная
проверка уведомлений; поле чека 54-ФЗ; Socket.IO через Redis для нескольких экземпляров сервера (тест с двумя
экземплярами). Docker-образ API собран и запущен: миграции, health, заголовки.
