# Подключение реальных провайдеров

> Проверено на этапе 13: подключение каждого провайдера — это **новый класс за готовым интерфейсом и одна строка
> в выборе провайдера** (`env.ts` + модуль). Бизнес-логика, база данных и приложения не меняются.
> Тестовые реализации остаются для разработки и автотестов; в production они запрещены (сервер не стартует).

## Платежи: что подготовлено на этапе 13

Реальные провайдеры работают асинхронно — это учтено, чтобы подключение ЮKassa не потребовало переделок:

* **Уведомления всех типов:** `payment.succeeded / cancelled`, `refund.succeeded / cancelled`,
  `payout.succeeded / cancelled`. Повторная доставка уведомления ничего не меняет (таблица `payment_webhook_events`) ✅.
* **Возвраты и выплаты «в обработке»:** если провайдер не ответил сразу, деньги не считаются возвращёнными/выплаченными
  до уведомления; отказ провайдера отмечается и уходит поддержке/финансисту ✅ (тест «асинхронные возвраты и выплаты»).
* **Возврат вызывается после фиксации транзакции** (заданием): раньше внешний вызов шёл внутри транзакции, и при её
  откате деньги могли вернуться без записи в учёте. Ключ идемпотентности тот же — повтор безопасен ✅.
* **Проверка уведомления асинхронная** (`parseWebhook` → Promise, передаётся IP отправителя): у ЮKassa уведомление
  подтверждается перезапросом статуса объекта по API или проверкой IP.
* **Чек 54-ФЗ:** в `CreatePaymentInput` есть необязательное поле `receipt` (покупатель, позиции, ставка НДС, предмет и
  способ расчёта). Заполняется после решения бухгалтера; до этого чек не передаётся.
* **Выплаты исполнителям** идут через `payout(...)` с реквизитами (БИК, счёт, ИНН). Какой продукт ЮKassa (или банк)
  будет выплачивать на счета ИП/ЮЛ — решение юриста по агентской схеме (С-34).
* Оплата юрлиц по счёту (банковский перевод) уже проводится функцией `recordExternalPayment` — источник подтверждения
  (выписка банка / ручное подтверждение финансиста) выбирается вместе с банком.

## Порядок подключения одного провайдера

1. Класс `XxxProvider implements <Интерфейс>` рядом с тестовым.
2. Значение в перечислении `XXX_PROVIDER` (`env.ts`) и ветка в фабрике модуля.
3. Ключи — в Lockbox, в env — только ссылка.
4. Контрактный тест провайдера в песочнице (у ЮKassa — тестовый магазин).
5. Перезапуск сценариев: `pnpm test`, `pnpm test:load`, сквозные сценарии приложений.
